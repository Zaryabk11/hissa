# Architecture

Hissa is an npm-workspaces monorepo: an Expo app, a Node/Express API (modular monolith) and a Supabase project.

```
hissa/
  frontend/            Expo + TypeScript + Expo Router
    app/               routes: landing, (onboarding) incl. avoids, (auth)/sign-in, (tabs)/today|scan|feel|social,
                       (scan)/scanning|review|plan|no-plate, (account)/profile, meals/[id], recipes/[id], inbox
    src/features/      <feature>/{components,hooks,api}: landing onboarding today scan plan nutrition
                       core (API client for the portion flow) social feel auth avoids recipes history profile
    src/shared/        api client (apiAuthed), auth (Supabase session, Google sign-in), theme, ui
    scripts/start.mjs  starts Expo advertising the .local hostname (decision 0004)
  backend/src/
    app.ts, server.ts
    shared/            config, db, errors, middleware, logger, time (PKT day)
    modules/<name>/    auth profiles scan nutrition plan meals streaks notifications friends goals feel recipes snaps
  backend/scripts/     synthetic-question-data.ts, train-question-ranker.ts, draft-recipes.ts, recipe-draft-guard.ts, sample-questions.ts (offline, not in the build)
  database/
    data/catalog.csv   the dish catalog (78 dishes), see data-sources.md
    scripts/           build-seed.mjs turns catalog.csv into seed.sql, plus tests
    supabase/          config.toml, migrations/, seed.sql (generated)
```

Status (2026-11-03): v1 (scan, nutrition, profiles, plan, meals) is built and connected to Expo. `streaks` implements saved-meal day marks and per-user streaks; `friends` (username search, requests, daily nudges), `goals` (one habit goal per user, celebrations, cheers) and `notifications` (the inbox) replaced the one-buddy pairs. `feel` implements due meal check-ins and, behind them, the per-user evidence model and the synthetic-trained question ranker, which picks the follow-up question that `GET /api/feel/question/:mealId` returns (Gemini words it, the service validates it). `auth` returns the current authenticated user. `GET /api/feel/pattern` returns the weekly pattern card (v2 Task 8 backend; the app card is not built). `feel` also stores one private "try next time" experiment per user (v2 Task 9 backend; the app part is built separately). `profiles` also owns the avoid list (`GET/PUT /api/profiles/me/avoids`, v3), and `recipes` serves reviewed recipes ranked for the caller with a one-tap "not for me" (v3); no recipe is reviewed yet, so none is served. Live status: `docs/superpowers/plans/2026-11-02-v2-status.md`.

## Backend rules

Each module under `backend/src/modules/<name>/` has these files:

```
<name>.routes.ts       HTTP routes only
<name>.controller.ts   maps HTTP to service calls, no business logic
<name>.service.ts      business rules
<name>.repository.ts   Supabase data access only
<name>.schemas.ts      zod request/response schemas
<name>.types.ts
index.ts               the module's ONLY public API
__tests__/
```

1. **Layer direction:** routes -> controller -> service -> repository. Never skip or reverse a layer.
2. **Module boundary:** a module imports another module only through that module's `index.ts`, never its repository or internals.
3. **External APIs sit behind clients** inside their module (`scan/gemini.client.ts`, `feel/gemini-question.client.ts`). Services take them as dependencies so tests can mock them. Nutrition has no external client: it reads the `dishes` table.
4. Every module is mounted at `/api/<name>` behind auth, except `GET /api/health`.

Both rules 1 and 2 are enforced by `no-restricted-imports` in `backend/eslint.config.mjs` (`npm run lint`).

Files beyond the standard set, as built:

```
scan/gemini.client.ts      Gemini REST client (structured output, injected into the service)
shared/image/              sharp: JPEG, longest side 1024 px, EXIF rotation applied (`resizePhoto`), plus the shared base64 `imageBodySchema` (scan and snaps)
shared/jobs/               `startJobs`: in-process timers for background jobs (the snap sweeper)
snaps/snap-storage.client.ts   Supabase Storage client for the `snaps` and `snap-reports` buckets (injected into the service)
snaps/snaps.sweeper.ts     the `snaps.sweep` job (every 5 minutes), added only when `SNAPS_ENABLED`
profiles/budget.ts         Mifflin-St Jeor daily calorie budget
feel/gemini-question.client.ts  Gemini REST client that only words one check-in question (injected into the service)
feel/question-bank.ts      the fixed question text and options, plus the wording guard
feel/question-model.ts     per-user evidence (whole-meal observations) and the intent ranker
feel/weekly-pattern.ts     pure weekly card rule (counts, 60% and 25 point cut-offs, `patternKey`)
feel/question-weights.ts   GENERATED by `npm run train:questions` (weights plus a training report)
shared/time/pkt.ts         PKT day helper (day string and UTC bounds)
```

Modules call each other only through `index.ts`: `scan` and `meals` use `nutrition`, `scan` also uses `profiles` (`isAvoided`), `recipes` uses `profiles`, `meals`, `nutrition` and `feel` (narrow `PatternSource`), `plan` uses `profiles`, `meals` and `nutrition`, `notifications` uses `profiles`, `friends` uses `streaks`, `profiles` and `notifications`, `goals` uses `streaks`, `friends`, `notifications` and `profiles`, `snaps` uses `friends`, `meals` and `profiles` (so `snaps -> friends, meals, profiles`), and `meals` calls `goals.onMealSaved` after `streaks.markMealSaved`. Notifications are inbox-only: rows read through `GET /api/notifications`, no push.

## Data flow for a scan

```
app photo -> scan: resize (sharp, 1024 px), daily cap check via scan_log,
             Gemini (dish slug from the catalog enum or "unknown" + portion + confidence)
          -> app correction chips for confidence below 0.6 or unknown
          -> plan: nutrition (per-100g from the dishes table x grams per unit)
             fitted to the remaining daily budget
          -> meals: save predicted AND confirmed items -> today's log
          -> streaks: mark the PKT day after meal items save
```

Gemini names dishes only from our catalog. Calories always come from the `dishes` table (`kcal_per_100g * grams_per_unit * units / 100`), never from Gemini and never stored per portion.

Gemini is called with a 10 s per-attempt timeout and up to 3 attempts for timeouts, 503 and 429 ([decision 0005](decisions/0005-gemini-timeouts-retries-and-model.md)); the default model is `gemini-flash-lite-latest`.

Over the daily cap (10 scans per user per PKT day, `SCAN_DAILY_CAP`) or when Gemini is unavailable, `POST /api/scan` returns `mode: "manual"` with a `reason` (`daily_cap` or `gemini_unavailable`) and the app lets the user pick dishes by hand. The scan flow never dead-ends.

## Database

RLS is on for every table. The backend uses the service role (bypasses RLS) and must scope every query to the authenticated user. Direct clients read only their own `streak_days`. Friends receive only username, display name, current logged flag, streak, nudge state and a goal the user chose to share through the authenticated API, never historical rows or meals. The one addition is the snap photo: it is returned only by `POST /api/snaps/:id/open`, never as a URL, and is deleted once every recipient has opened it or after 24 hours; a photo someone reports is kept 30 days for review. Snaps and the streak cheer are built behind `SNAPS_ENABLED` (off by default, see "Snaps" below); public accounts, following, food cheers and custom goals are designed, not built (`docs/superpowers/specs/2026-11-06-snaps-follows-cheers-design.md`).

Migrations in `database/supabase/migrations/`:

- `20261030000000_initial_schema.sql`: `profiles`, `dishes`, `meals`, `meal_items`, `streak_days`, `feel_checkins`, RLS policies.
- `20261101000000_catalog_and_scan_log.sql`: `dishes` gets per-100g columns (`kcal_per_100g` and macros), `source`, `basis`, `unit_basis` and the `bowl` unit; FatSecret and per-unit columns are dropped. New table `scan_log` (one row per scan per user per PKT day) backs the daily cap.
- `20261102000000_profiles_on_signup.sql`: a trigger on `auth.users` creates a `profiles` row at sign-up (with a backfill for existing users), because meals and `scan_log` reference `profiles(id)`.
- `20261102000100_revoke_handle_new_user_execute.sql`: the trigger function cannot be called through the API.
- `20261102000200_buddy_invites_and_privacy.sql`: the one-buddy invite RPC and no direct client access to the pairs table (both dropped by `20261104000000`).
- `20261102000300_buddy_nudges.sql`: the buddy nudge table and status RPC (dropped by `20261104000000`), owner-only `streak_days` reads, and **no direct client writes** to `meals` and `meal_items` (owners keep select-only policies).
- `20261102000400_feel_learning.sql`: `feel_checkins` gets `symptom`, `question_type`, `answer_id`, `question_source`; a composite foreign key ties a check-in to its meal's owner; direct client writes to `feel_checkins` are revoked.
- `20261102000500_user_experiments.sql`: `user_experiments` (one private choice from a weekly card: `pattern_key`, `action`, `status` active or tried, `tried_meal_id` tied to the owner's meal by a composite foreign key), a unique partial index allowing one `active` row per user, owner select-only RLS, and no direct client writes. Applied to the hosted project (repaired and verified 2026-11-04).
- `20261103000100_meal_delete.sql`: backend-only functions `meal_delete(actor_id, meal_id)` and `meal_replace_items(actor_id, meal_id, total, items)`, executable by `service_role` only. Each is one transaction scoped to the actor: delete removes the meal (items and check-ins cascade, `user_experiments.tried_meal_id` is set null) and the PKT day's `streak_days` row when no other meal with a confirmed item remains that day; replace swaps the items and total. Applied to the hosted project (repaired and verified 2026-11-04).
- `20261104000000_friends_goals_notifications.sql`: `profiles.username`, `friendships`, `goals`, `notifications`; migrates active buddies into friendships and drops `buddy_pairs`, `buddy_nudges` and their RPCs. Backend (service role) only. Applied to the hosted project (verified 2026-11-04); detail under "Friends, goals and notifications".
- `20261104000100_v3_avoids_recipes.sql`: `dishes.protein_type`, `user_avoids` (per user, a dish or a protein), `recipes` (one per catalog dish, `reviewed` flag), `recipe_feedback` ("not for me"), owner select-only RLS and no direct client writes. **Applied and smoke-tested on a local Supabase stack (`database/scripts/smoke-v3-local.mjs`, 2026-11-04); applied to the hosted project 2026-11-04 (hosted `recipes` is empty: the seed was not loaded, and no recipe is reviewed).**
- `20261105000000_macro_targets.sql`: nullable `profiles.protein_target_g`, `carbs_target_g`, `fat_target_g` (integers 1-1000). **Not yet applied to the hosted project.**
- `20261106000000_snaps.sql`: tables `snaps`, `snap_recipients` and `reports` (RLS on, all client access revoked), the `cheer_streak` notification kind with one per actor, user and day, the private `snaps` and `snap-reports` Storage buckets (JPEG only, 500 KB limit), and it drops `meals.photo_path`. **Not yet applied to the hosted project.**

All of the migrations above except `20261105000000` and `20261106000000` are applied to the hosted project `zvhwzekbgmuaaiepkcwn` (the friends and v3 migrations verified 2026-11-04; `20261102000500` and `20261103000100` were applied after a remote history repair). Direct clients never write meals, check-ins, friend, goal or notification data: everything goes through the API ([decision 0006](decisions/0006-v2-learning-loop-and-backend-only-writes.md)).

`dishes` is seeded from `database/data/catalog.csv` by `database/scripts/build-seed.mjs` (generated `seed.sql`, upsert only). Sources and portion rules are in [data-sources.md](data-sources.md).

## Meal history, edit and delete

`meals` also serves `GET /api/meals/week`, `/history`, `/:id`, `PATCH /:id` and `DELETE /:id` (see `backend/README.md`). History and week totals group the caller's meals by PKT day in the service (one range query via `listMealsBetween`). Edits recompute totals with the same pricing code as a save (`priceItems`). The repository calls the two migration functions through RPC, so the delete, the streak-day removal and the item swap are each atomic; `supabase-js` has no transaction and ordered client-side calls could leave a half-deleted meal. For that reason `meals` does not call `streaks` for removal: the function owns the `streak_days` cleanup, using the same "has a confirmed item" rule as the status repair, so a status read cannot bring the day back. Editing never changes `eaten_at`, so no streak change is needed.

## Friends, goals and notifications

- Migration `20261104000000_friends_goals_notifications.sql` adds `profiles.username`, `friendships` (one row per pair, `user_low < user_high`, status pending/active/declined/removed), `goals` (one active goal per user, `streak` or `window`, optional `shared`) and `notifications`; it migrates active buddies into friendships and drops the old pair, nudge and RPC objects. All are backend (service role) only. Applied to the hosted project (verified 2026-11-04).
- Registry order: `auth, profiles, nutrition, scan, streaks, notifications, friends, goals, meals, plan, feel, recipes`, then `snaps` (built after `recipes`, mounted only when `SNAPS_ENABLED=true`).
- `meals` calls `streaks.markMealSaved`, then `goals.onMealSaved(userId)` in its own try/catch: a failed goal check is logged (`Goal check failed`) and never fails the save. `goals` reads logged days itself, so it must run after the `streak_days` row is written.
- `GET /api/streaks` returns exactly `streak` and `loggedToday` for the caller (a day counts when a meal is saved). A friend's row from `GET /api/friends/overview` carries only `userId`, `username`, `displayName`, `streak`, `loggedToday` and `nudgedToday`; a friend sees a goal only when its owner marked it shared.
- `POST /api/friends/:userId/nudge` sends one in-app nudge per sender per PKT day, only while the friend has not logged. Notifications are inbox-only (`GET /api/notifications`, `POST /api/notifications/read`): there is no push.

## Snaps

A snap is the photo of a meal, sent to the sender's active friends right after the meal is saved. Behind `SNAPS_ENABLED` (backend) and `EXPO_PUBLIC_SNAPS_ENABLED` (app); both default to off. When the backend flag is off the `snaps` router is not mounted (404) and the sweeper does not start. `POST /api/friends/:userId/cheer-streak` is not flag-gated.

- **Send** (`POST /api/snaps`, `{ mealId, image, mimeType }`): the meal must be the caller's and at most 30 minutes old, one snap per meal (409), at most 12 snaps per PKT day (429). The photo is resized with `resizePhoto` (JPEG, 1024 px, EXIF applied) and stored as `<uuid>.jpg` in the private `snaps` bucket; one `snap_recipients` row per active friend freezes the audience at send time. With no friends nothing is stored and the response is `{ id: null, expiresAt: null, recipients: { friends: 0 } }`. A failed insert removes the object again.
- **Inbox** (`GET /api/snaps/inbox`): unopened, unexpired snaps from current senders, as sender card, `sentAt` and `expiresAt`. It never carries the photo, and listing it does not consume a snap.
- **Open** (`POST /api/snaps/:id/open`): the only way to get the photo. The service checks the recipient row, expiry and that sender and caller are still friends, reads the bytes from Storage, then claims the open with an atomic update (`opened_at is null`); two racing opens cannot both succeed. The response is base64 JPEG with `Cache-Control: no-store`; no signed URL is ever issued. Every failure (not a recipient, already opened, expired, deleted, unfriended, missing object) is the same 404.
- **Report** (`POST /api/snaps/:id/report`, reason `spam | inappropriate_photo | harassment | other`): only a recipient who opened the snap can report it. The photo is copied to the private `snap-reports` bucket, a `reports` row records it (one per reporter and snap), and the copy is kept 30 days (`evidence_expires_at`). The original is never touched.
- **Unsend** (`DELETE /api/snaps/:id`): the sender removes the object, then the rows are marked deleted and the recipients removed. If the object removal fails the rows stay and the sender can retry.
- **Streak cheer** (`POST /api/friends/:userId/cheer-streak`): a friend who logged today on a streak of 3 or more gets a `cheer_streak` inbox notification, at most one per cheerer, friend and PKT day (409 on a repeat). It is an inbox row like a nudge; there is no push.
- **Buckets:** `snaps` holds live photos and `snap-reports` holds reported copies; both are private, JPEG only, 500 KB per object. Clients have no Storage access: only the backend (service role) reads and writes them.
- **Sweeper** (`snaps.sweep`, every 5 minutes and once at start): deletes by state, not schedule, so a restart catches up. Object first, then the row, so a failure leaves the row and the next run retries. Stages: snaps expired or opened more than 10 minutes ago (the report window; the object is removed, the row marked deleted); objects older than 25 hours no live row owns; report copies past `evidence_expires_at`; report copies older than 31 days no report row points at; deleted rows older than 7 days are purged. Logs carry ids and counts only, never image data or who opened a snap. Timers are in-process (`startJobs`), so this assumes one API instance.
- **Bodies:** `/api/snaps` and `/api/scan` accept an 8 MB JSON body after auth (413 above that), and `imageBodySchema` caps the decoded photo at 6,000,000 bytes (400); the app does not downscale large photos yet, so a photo near that size is refused.
- **Privacy:** photo bytes are never logged, never returned by any route except open, and Gemini never sees snaps. Friends and the friends overview carry no photo or snap fields.

## Food and Feel (check-in and learning)

- `GET /api/feel/due` returns the oldest meal of the caller that is at least 90 minutes and at most 24 hours old, has at least one confirmed dish and no check-in (or `null`). The optional query `?skip=id,id` steps past meals the user skipped on the screen. `POST /api/feel/checkins` accepts `energy` (`low|okay|good`), `stomach` (`heavy|fine|light`), an optional `symptom` (`bloated|upset|other|not_sure`, offered only after a heavy stomach) and an optional `questionType: "pre_existing"` with `answerId` (`yes|no|not_sure`); one check-in per meal, enforced by a unique constraint. Skipping writes nothing. `GET /api/feel/question/:mealId` returns the follow-up question for a due meal: `FeelService.getQuestion` builds the owner's evidence (check-ins made within 24 hours of their meal; the cut-off lives in the service), uses the fixed `symptom_detail` intent, and sends Gemini only the intent, the allowed option ids and a one-line aggregate summary (check-in count, whether a dish repeats). The text is used only if it passes the wording guard (an allowlist of words) and Gemini returned exactly the allowed ids; the options always come from the question bank. Otherwise `source` is `fallback` and the fixed text is used. Gemini never supplies options, counts, calories or health claims.
- `listObservations(userId)` (repository) returns whole-meal observations for that user only: confirmed dishes and the check-in time. `FeelService.getQuestion` drops check-ins made more than 24 hours after their meal (the cut-off lives in the service), then `buildEvidence` (`question-model.ts`) turns the rest into counts. `GET /api/feel/question/:mealId` calls it.
- `GET /api/feel/pattern` runs `weeklyPattern` (`weekly-pattern.ts`, pure logic) over the caller's own `listObservations` rows (check-ins made within 24 hours of their meal). The 7-day window is keyed on the meal's `eatenAt`, not the check-in time. It reads the whole history per call (the same `ponytail:` ceiling as the evidence model).
- **Experiments.** `FeelService.createExperiment` recomputes the caller's weekly card and accepts only that card's `patternKey`, then inserts through the repository; the database enforces one `active` experiment per user and the owner link of the tried meal. `markExperimentTried` accepts only the owner's own meal saved after the experiment was created. Experiments are reachable only through `/api/feel/experiments*`; the `streaks`, `friends` and `goals` modules never read or import them (a test scans the source for this). The optional backend `DEMO_USER_ID` is the only user whose weekly card is `isSample: true`; `database/scripts/seed-demo-history.mjs` seeds sample history for that one account.
- **`pre_existing` is a skippable follow-up.** `GET /api/feel/question/:mealId` serves `symptom_detail` by default (the ranker, `rankQuestions`, is still not consulted). With `?stomach=heavy&after=symptom_detail` (the app has a heavy stomach and the symptom step answered) `getQuestion` instead returns the fixed `pre_existing` question (`source: fallback`, never sent to Gemini) unless the user's latest stored `question_type = 'pre_existing'` check-in (read through the repository, scoped to the user) is under 14 days old; if that lookup fails it serves the usual question. `POST /api/feel/checkins` stores the answer in the existing `question_type`, `answer_id` and `question_source` columns (a strict pair: both or neither). `attributable()` in the service drops a meal whose stored answer is `yes` from the weekly pattern and the per-user model; `no` and `not_sure` change nothing. The answer is never read by the `streaks`, `friends` and `goals` modules and is not logged (a test scans for both).
- Gemini is sent only the intent, the allowed option ids and a one-line aggregate summary (check-in count, and whether a dish repeats with its exposed and comparison meal counts; no dish names, ids, meal history or friend data). It has at most 2 attempts within an 8 second overall deadline, so a request waits at most about 8 seconds before the fixed question is used. The service caches each answer per user and meal for 10 minutes (per process, at most 500 entries) so repeated requests do not re-call Gemini. If the history cannot be read, the fixed question is returned instead of an error.
- The wording guard is an **allowlist**: one short question starting with how, what or which, ASCII letters only, ending in `?`, at most 120 characters, about the stomach or discomfort, and every word taken from a small fixed vocabulary. It checks vocabulary and shape, not meaning. Options, their order and labels always come from the question bank.

## Google sign-in

Supabase Auth with the Google provider and PKCE; the app opens the browser sheet, receives `?code=` and exchanges it (`frontend/src/shared/auth/google.ts`). The session is stored in SecureStore and refreshed; `apiAuthed` attaches the bearer token and signs the user out on a 401. Route guards in `frontend/app/_layout.tsx` keep `(tabs)` and `(scan)` closed without a session. Return-address rules and project settings: [decision 0004](decisions/0004-google-sign-in-return-address.md).

## Avoids and recipes (v3)

`profiles` owns the avoid list and exports `isAvoided` through its `index.ts`; `scan` uses it to set `ScanItem.avoided`. The `recipes` module reads `profiles` (budget, avoids), `meals` (calories today, dish counts), `nutrition` (catalog) and a narrow `PatternSource` slice of `feel`, all through their `index.ts`. `rank.ts` is a pure function. Recipes come from `database/data/recipes.json` through the seed builder; `backend/scripts/draft-recipes.ts` asks Gemini for drafts offline (banned-word guard `recipe-draft-guard.ts`), writes them as `reviewed: false`, and only reviewed rows are served.
