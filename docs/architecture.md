# Architecture

Hissa is an npm-workspaces monorepo: an Expo app, a Node/Express API (modular monolith) and a Supabase project.

```
hissa/
  frontend/            Expo + TypeScript + Expo Router
    app/               routes: landing, (onboarding), (auth)/sign-in, (tabs)/today|scan|feel|buddy,
                       (scan)/scanning|review|plan|no-plate, invite/[code]
    src/features/      <feature>/{components,hooks,api}: landing onboarding today scan plan nutrition
                       core (API client for the portion flow) buddy feel auth
    src/shared/        api client (apiAuthed), auth (Supabase session, Google sign-in), theme, ui
    scripts/start.mjs  starts Expo advertising the .local hostname (decision 0004)
  backend/src/
    app.ts, server.ts
    shared/            config, db, errors, middleware, logger, time (PKT day)
    modules/<name>/    auth profiles scan nutrition plan meals streaks feel
  backend/scripts/     synthetic-question-data.ts, train-question-ranker.ts (offline, not in the build)
  database/
    data/catalog.csv   the dish catalog (78 dishes), see data-sources.md
    scripts/           build-seed.mjs turns catalog.csv into seed.sql, plus tests
    supabase/          config.toml, migrations/, seed.sql (generated)
```

Status (2026-11-03): v1 (scan, nutrition, profiles, plan, meals) is built and connected to Expo. `streaks` implements invitations, saved-meal status, shared streaks and in-app daily nudges. `feel` implements due meal check-ins and, behind them, the per-user evidence model and the synthetic-trained question ranker (not yet exposed over HTTP). `auth` returns the current authenticated user. Not built yet: the Gemini-drafted question, the weekly pattern card and the private experiment (v2 Tasks 7 to 9). Live status: `docs/superpowers/plans/2026-11-02-v2-status.md`.

## Backend rules

Each module under `backend/src/modules/<name>/` has these files:

```
<name>.routes.ts       HTTP routes only
<name>.controller.ts   maps HTTP to service calls, no business logic
<name>.service.ts      business rules
<name>.repository.ts   Supabase data access only
<name>.schemas.ts      zod request/response schemas
<name>.types.ts
index.ts               the module's ONLY public API
__tests__/
```

1. **Layer direction:** routes -> controller -> service -> repository. Never skip or reverse a layer.
2. **Module boundary:** a module imports another module only through that module's `index.ts`, never its repository or internals.
3. **External APIs sit behind clients** inside their module (`scan/gemini.client.ts`). Services take them as dependencies so tests can mock them. Nutrition has no external client: it reads the `dishes` table.
4. Every module is mounted at `/api/<name>` behind auth, except `GET /api/health`.

Both rules 1 and 2 are enforced by `no-restricted-imports` in `backend/eslint.config.mjs` (`npm run lint`).

Files beyond the standard set, as built:

```
scan/gemini.client.ts      Gemini REST client (structured output, injected into the service)
scan/resize-photo.ts       sharp: JPEG, longest side 1024 px, EXIF rotation applied
profiles/budget.ts         Mifflin-St Jeor daily calorie budget
feel/question-model.ts     per-user evidence (whole-meal observations) and the intent ranker
feel/question-weights.ts   GENERATED by `npm run train:questions` (weights plus a training report)
shared/time/pkt.ts         PKT day helper (day string and UTC bounds)
```

Modules call each other only through `index.ts`: `scan` and `meals` use `nutrition`, `plan` uses `profiles`, `meals` and `nutrition`.

## Data flow for a scan

```
app photo -> scan: resize (sharp, 1024 px), daily cap check via scan_log,
             Gemini (dish slug from the catalog enum or "unknown" + portion + confidence)
          -> app correction chips for confidence below 0.6 or unknown
          -> plan: nutrition (per-100g from the dishes table x grams per unit)
             fitted to the remaining daily budget
          -> meals: save predicted AND confirmed items -> today's log
          -> streaks: mark the PKT day after meal items save
```

Gemini names dishes only from our catalog. Calories always come from the `dishes` table (`kcal_per_100g * grams_per_unit * units / 100`), never from Gemini and never stored per portion.

Gemini is called with a 10 s per-attempt timeout and up to 3 attempts for timeouts, 503 and 429 ([decision 0005](decisions/0005-gemini-timeouts-retries-and-model.md)); the default model is `gemini-flash-lite-latest`.

Over the daily cap (10 scans per user per PKT day, `SCAN_DAILY_CAP`) or when Gemini is unavailable, `POST /api/scan` returns `mode: "manual"` with a `reason` (`daily_cap` or `gemini_unavailable`) and the app lets the user pick dishes by hand. The scan flow never dead-ends.

## Database

RLS is on for every table. The backend uses the service role (bypasses RLS) and must scope every query to the authenticated user. Direct clients read only their own `streak_days`. Buddies receive only current logged flags, shared streak and nudge state through the authenticated API, never historical rows or meals.

Migrations in `database/supabase/migrations/`:

- `20261030000000_initial_schema.sql`: `profiles`, `dishes`, `meals`, `meal_items`, `buddy_pairs`, `streak_days`, `feel_checkins`, RLS policies.
- `20261101000000_catalog_and_scan_log.sql`: `dishes` gets per-100g columns (`kcal_per_100g` and macros), `source`, `basis`, `unit_basis` and the `bowl` unit; FatSecret and per-unit columns are dropped. New table `scan_log` (one row per scan per user per PKT day) backs the daily cap.
- `20261102000000_profiles_on_signup.sql`: a trigger on `auth.users` creates a `profiles` row at sign-up (with a backfill for existing users), because meals and `scan_log` reference `profiles(id)`.
- `20261102000100_revoke_handle_new_user_execute.sql`: the trigger function cannot be called through the API.
- `20261102000200_buddy_invites_and_privacy.sql`: `declined` pair status, service-only `buddy_invite_operation` RPC (one transaction lock for create, accept, decline, end; one buddy per person), and no direct client access to `buddy_pairs`.
- `20261102000300_buddy_nudges.sql`: `buddy_nudges` (one per sender per day), service-only `buddy_status_operation` RPC, owner-only `streak_days` reads, and **no direct client writes** to `meals` and `meal_items` (owners keep select-only policies).
- `20261102000400_feel_learning.sql`: `feel_checkins` gets `symptom`, `question_type`, `answer_id`, `question_source`; a composite foreign key ties a check-in to its meal's owner; direct client writes to `feel_checkins` are revoked.

All of these are applied to the hosted project `zvhwzekbgmuaaiepkcwn` (verified 2026-11-02). Direct clients never write meals, check-ins or buddy data: everything goes through the API ([decision 0006](decisions/0006-v2-learning-loop-and-backend-only-writes.md)).

`dishes` is seeded from `database/data/catalog.csv` by `database/scripts/build-seed.mjs` (generated `seed.sql`, upsert only). Sources and portion rules are in [data-sources.md](data-sources.md).

## Saved-meal buddy status

The registry injects the streaks public service into meals. Successful item insertion calls `markMealSaved(userId, eatenAt)` with the database timestamp; failed item insertion never marks a day. A failed mark is logged while the meal remains saved. A subsequent status read repairs missed marks from complete meals with confirmed items, including the active partner only after checking pair membership.

`GET /api/streaks` returns exactly `pairStatus`, `pendingInviteCode` (the creator's own pending code), `streak`, `ownLoggedToday`, `buddyLoggedToday`, `unreadNudge`, and `nudgedToday` (whether the caller already sent today's nudge). The shared streak counts consecutive days with both logged since the pair's acceptance PKT day. Today may remain in progress without erasing yesterday's completed streak. PKT is UTC+05:00.

`POST /api/streaks/nudge` sends one in-app nudge per sender per PKT day only while the active buddy has not logged. `POST /api/streaks/nudge/ack` acknowledges only the caller's received nudges in the current pair. Ending a pair hides its old delivery state. The service-only `buddy_status_operation` RPC scopes reads to the actor and active pair; it shares the invitation transaction lock so ending a pair and sending a nudge cannot race. `20261102000300_buddy_nudges.sql` adds sender/day uniqueness, recipient read state, and owner-only streak RLS. Internal day arrays are projected away by the service before any HTTP response.

## Food and Feel (check-in and learning)

- `GET /api/feel/due` returns the oldest meal of the caller that is at least 90 minutes and at most 24 hours old, has at least one confirmed dish and no check-in (or `null`). The optional query `?skip=id,id` steps past meals the user skipped on the screen. `POST /api/feel/checkins` accepts `energy` (`low|okay|good`), `stomach` (`heavy|fine|light`) and an optional `symptom` (`bloated|upset|other|not_sure`, offered only after a heavy stomach); one check-in per meal, enforced by a unique constraint. Skipping writes nothing.
- `listObservations(userId)` (repository) returns whole-meal observations for that user only: confirmed dishes, check-ins made within 24 hours of the meal. `buildEvidence` and `rankQuestions` (`question-model.ts`) turn them into an ordered list of approved question types, falling back to the fixed order when there are fewer than 2 observations or no usable dish candidate. Nothing calls them over HTTP yet (Task 7).
- The 24 hour attribution cutoff currently lives in the repository; AGENTS.md rule 4 says repositories hold no business rules, so Task 7 should move it into the service.

## Google sign-in

Supabase Auth with the Google provider and PKCE; the app opens the browser sheet, receives `?code=` and exchanges it (`frontend/src/shared/auth/google.ts`). The session is stored in SecureStore and refreshed; `apiAuthed` attaches the bearer token and signs the user out on a 401. Route guards in `frontend/app/_layout.tsx` keep `(tabs)` and `(scan)` closed without a session. Return-address rules and project settings: [decision 0004](decisions/0004-google-sign-in-return-address.md).
